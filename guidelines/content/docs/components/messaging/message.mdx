## Overview

Messages provide compact, contextual feedback near the relevant interaction or content. They hug their content and float with a shadow rather than stretching full-width. Messages are automatically dismissed after a defined period or when the relevant content changes.

### When to use

Use a message when:
- The feedback is brief and relates to a specific interaction or content area.
- The feedback is small and local, such as confirming that a link was copied or an item was duplicated.
- An action also changes surrounding content or elements, such as adding an item to a list.

Consider another component when:
- The feedback belongs to a single form field — use the field's own help or validation text.
- The information needs prominent attention — use [Alert](/docs/components/messaging/alert) instead.
- The message requires user action but should not block the UI — use [Toast](/docs/components/messaging/toast).
- The message needs to interrupt the user and block further action until resolved — use a [Dialog](/docs/components/messaging/dialogs).

## Position, Hug & Dismissal

### Position

Messages are positioned close to the interaction or content they refer to. Their placement should make the relationship clear without obscuring relevant content.

### Hug

Messages use a self-sized layout that hugs their content rather than stretching to fill the available width. The container grows according to the text and optional inline link.

### Dismissal behaviour

Messages are automatically dismissed after a defined period or when the relevant content changes. They do not provide a manual dismiss control.

- Use timed dismissal for brief, non-essential feedback.
- Use content-change dismissal when the feedback should remain visible as long as the related content stays unchanged.
- Allow sufficient time to read and interact with the message, including actions such as Undo. [See accessible timing](#dismissal--timing)
- If users need control over dismissal, use an Alert instead.

## Accessibility

#### Semantics

- Give the message `role="status"` so assistive tech picks it up as a polite live-region update without stealing focus.
- Mark the icon `aria-hidden="true"` — it duplicates the color/text signal already carried by the message.

#### Focus 

- A message that appears in response to an action shouldn't steal keyboard focus — announce it, don't move focus to it.
- If a message includes an "Undo" or similar link, make it a real focusable `<button>`/`<a>`, not a styled `<span>` with a click handler.

#### Dismissal & Timing
- Ensure users have sufficient time to perceive and interact with messages, including users relying on assistive technologies.
- Use 5 seconds as a starting point for brief, non-interactive messages. Adjust the duration based on content complexity and interaction requirements, and validate it through usability testing rather than treating it as a fixed rule.
- Do not dismiss messages while users are interacting with them.
- Ensure important information and actions remain accessible after the message disappears.

## Implementation

No JavaScript is required for a static message.

```html
<link rel="stylesheet" href="namirial-theme.css">

<div class="nm-message nm-message--positive" role="status">
  <span class="nm-message__icon" aria-hidden="true"><!-- icon --></span>
  <span>Draft saved</span>
  <span class="nm-message__link">Undo</span>
</div>
```

#### CSS classes

| Class | Values | Default |
|-------|--------|---------|
| `nm-message--{intent}` | primary · secondary · accent · info · positive · negative · warning — omit for `info` | — (`info`) |
| `nm-message__icon` | Leading icon slot, 24×24px | — |
| `nm-message__link` | Inline emphasized link, shares icon color | — |
